# 如何让 AI 根据需求完成一个功能的开发

## 研究问题

> **如何将一份需求文档和一张 UI 图，拆成 AI 能安全执行、团队能独立验收的开发子任务？**

这个问题可以再拆成五个具体问题，恰好对应分享的五个环节：

1. **需求澄清**：哪些是文档明确写出的规则，哪些只是 UI 示例，哪些仍需产品决定？
2. **任务分解**：怎样把功能拆到每个 Agent 都有清晰输入、改动范围、交付物和完成标准？
3. **设计与编码**：前端、后端共享什么契约，哪些工作可以并行，哪些必须按顺序完成？
4. **编译、测试、Review**：怎样用实际命令、测试数据和页面行为证明功能符合需求？
5. **迭代和回退**：AI 理解错需求、多个 Agent 改动冲突或出现回归时，如何定位并恢复？

### 研究结论

**一个 Agent **：它的目标可观察，输入有来源，文件与责任边界明确，依赖已满足，完成后能用测试或操作步骤判断对错。缺少其中任何一项，就先补任务定义或澄清需求，再交给实现 Agent。

**多 Agent **：在于把不同职责的上下文和产物分开：产品梳理规则，规划者安排依赖，前后端实现各自范围，测试者验证行为，审查者独立看风险。真正可以并行的是**文件不冲突、共享契约已确定**的工作；否则并行只会把等待和冲突转移到集成阶段。

**可验证的交付**不是“AI 说完成了”，而是需求编号能追溯到任务、代码改动、测试报告（含前后对比截图）和最终验收记录。未执行的检查要写“未验证”。

### 一：需求澄清

需求澄清的目标不是把文档重写一遍，而是给每条规则标上**来源、确认状态、可验证方法**。

#### 文档中已明确的规则

| ID | 规则 | 对开发的影响 |
|---|---|---|
| R1 | 相关搜索框和任务名称输入框最多输入 21 个字，超出不能输入 | 输入组件与提交参数都要检查 |
| R2 | 高级搜索包含任务名称、任务模块、用户、归属空间、求解资源类型和时间等条件；多个字段支持多选 | 需要统一的条件数据结构 |
| R3 | 认证状态影响高级搜索面板可用内容；未认证时显示提示 | 需要覆盖两种企业状态 |
| R4 | 云端当前不提供 GPU 筛选；私有化环境可显示 GPU，用户选项结构也不同 | 环境差异要进入验收矩阵 |
| R5 | 点击搜索后关闭面板，已配置条件显示在搜索框下；多选标签仅露出一项并标示总数 | 面板、标签和查询参数需要同步 |
| R6 | 清除单个标签时，相应面板值也清除，明细表联动；重置使面板内容恢复默认 | 明确“草稿条件”和“已应用条件”的状态变化 |
| R7 | 默认按项目分组；取消分组后按任务操作逐条显示 | 切换展示方式，不能改变资源数据范围 |
| R8 | 未搜索时显示全部任务核时数合计，搜索后只合计命中任务；按四位小数展示 | 列表与合计必须依据同一筛选结果 |
| R9 | 资源分配页使用企业资源范围，资源明细页使用团队资源范围 | 服务端必须按身份约束数据范围 |

**举例**

> 比如 R6，初看只是“标签可以删除”。展开后其实是三件事：界面上的标签消失、重新打开面板时该字段已清空、查询结果和合计重新计算。一个模糊句子变成了三个可观察结果，AI 就能知道怎样做，测试也知道怎样验。

#### 文档未完全定死的问题

| 问题 | 如果 AI 自行猜测，会出现什么风险 | 推荐动作 |
|---|---|---|
| 不同字段之间是“且”还是“或”？同字段多选如何组合？ | 命中记录不正确 | 请产品用具体记录举例确定 |
| 时间范围是否包含起止当天、使用哪个时区、按哪一个时间字段过滤？ | 边界记录遗漏或误入 | 确定边界样例与时间字段 |
| 普通搜索框与高级搜索任务名称是否同时生效？ | 两套状态互相覆盖 | 确定交互和请求参数 |
| 点击重置后是否立即更新列表？ | 草稿条件和已应用条件不一致 | 确定重置的生效时机 |
| “21 个字”如何计算英文、空格和表情？ | 前端与后端长度校验不一致 | 对齐输入和接口规则 |
| 搜索历史引用的“文件列表”规则是什么？ | 搜索记录行为缺失 | 补充被引用文档或核对现有实现 |

**.md文件**：一页“已确认规则 + 待确认问题”。`product` 负责从用户场景整理规则，主代理负责把影响业务结果的未决问题带回给有权决定的人；`planner` 不把猜测写成确定任务。

### 二：任务分解与多 Agent 分工

**判断任务是否可交给 AI 的五问**：目标是什么？输入依据是什么？允许改哪里？依赖谁先完成？怎么验收？五问答不清，任务就还没有拆好。

| 顺序 | 角色 | 子任务 | 产物和完成标准 | 能否并行 |
|---|---|---|---|---|
| T0 | `product` | 整理用户场景、确定规则、列出待确认问题 | 有来源的需求清单和验收样例 | 先做 |
| T1 | `planner` | 阅读现有项目，定义接口契约、依赖和文件归属 | 填好的任务卡，前后端共享字段明确 | 依赖 T0 |
| T2 | `backend` | 实现查询条件、权限范围、结果与合计逻辑 | 接口行为与后端测试结果 | 与 T3 有条件并行 |
| T3 | `frontend` | 实现面板、搜索、标签、分组和状态同步 | 页面行为与前端检查结果 | 与 T2 有条件并行 |
| T4 | 主代理 | 集成前后端，核对接口与实际页面 | 集成改动及冲突处理记录 | 依赖 T2、T3 |
| T5 | `tester` | 按验收矩阵验证主路径、边界与回归 | 通过、失败、未验证三类结果，每条用例附前后对比截图，并汇总测试报告 | 依赖 T4 |
| T6 | `reviewer` | 独立审查需求覆盖、正确性与风险 | 带位置和复现步骤的发现 | 依赖集成与验证证据 |

**讲述稿**

> 多 Agent 不等于同时喊六个角色开工。T0 和 T1 是先后依赖；T2 与 T3 只有在请求字段、响应结构和权限口径确定后才适合并行。测试可以提前设计用例，但最终行为验证必须等集成结果出来。Reviewer 最后独立看一遍，避免实现者只检查自己知道的路径。
>
> 前后端都在同一项目时需要写文件归属。如果前端和后端都去改同一个接口定义文件，就不能简单并行；先由一个角色定契约，再让另一个角色消费。这样多 Agent 才是在缩短等待，而不是制造冲突。

**.md文件**：工作区中的 `.codex/agents/planner_task.md`它是 Agent 之间交接的“共同账本”。


### 三：设计与编码

**接口契约最少要说清**：每个筛选字段的名称和类型、多选值编码、空值含义、条件组合、时间边界、分页与排序、企业/团队数据范围、核时数合计口径、错误响应。

> 设计阶段不要求一开始就把所有代码写完，但必须先画出数据如何走。页面里可以有两个条件集合：面板里正在编辑的是草稿，列表当前使用的是已应用条件。点击搜索时，草稿变成已应用；删除标签时，已应用条件变化，同时面板也要同步。
>
> 后端的重点是查询和权限。前端隐藏 GPU 选项，不能代替服务端控制数据。资源分配页和资源明细页使用不同范围，这个边界应由后端依据当前身份执行。两边都按同一个契约工作，才能在集成时少猜字段。

**让 AI 分轮工作**：

1. **现状轮**：只读项目，列已有页面、接口、测试和缺口。
2. **约定轮**：给出字段、状态与待确认问题，不修改代码。
3. **实施轮**：按任务卡限制文件范围，分开实现前后端。
4. **集成轮**：主代理检查接口参数、页面行为、权限和合计是否一致。

```text
先让 product 将需求和 UI 分成已确认规则、待确认问题和验收样例；
再让 planner 按 .codex/agents/planner_task.md 生成任务卡，写清接口契约、任务依赖和文件归属。
契约确定后，将互不冲突的后端和前端任务分别交给 backend 与 frontend。
两者交接后，由主代理集成，tester 依据验收矩阵验证，reviewer 独立只读审查。
对会改变查询结果、权限或统计口径的歧义，不自行决定。
```

### 四：编译、测试、Review

“编译通过”只证明代码能通过某项构建检查；“测试通过”也只覆盖实际运行过的用例。验收必须从 R1–R9 反向检查。

| 需求 | 操作与测试数据 | 期待看到的结果 | 证据类型 |
|---|---|---|---|
| R1 输入限制 | 在任务名称输入框输入第 22 个字 | 超出部分不能进入输入值，提交参数不超限 | 前后对比截图、请求参数 |
| R2 多选 | 在任务模块中选两项 | 面板保存两项，请求包含两项 | 前后对比截图、请求参数 |
| R3、R4 状态差异 | 分别使用已认证/未认证、云端/私有化环境 | 可用条件和提示符合对应规则 | 四种状态的前后对比截图 |
| R5、R6 标签同步 | 搜索后删除一个“归属空间”标签 | 标签、面板、列表和合计同步改变 | 前后对比截图、结果数据 |
| R7 分组 | 切换“分组展示” | 项目分组与任务逐条展示切换 | 前后对比截图 |
| R8 合计 | 用固定任务数据，筛选出其中一部分 | 合计只包含命中任务，显示四位小数 | 测试数据、手算结果、前后对比截图 |
| R9 数据范围 | 准备跨企业或跨团队数据 | 当前身份只能取到允许范围内的记录 | 接口返回数据、前后对比截图 |

**.md**
> `tester` 找的是行为与验收标准的差异；`reviewer` 从代码和证据里找遗漏的风险。两个角色关注点不同，都应把“没测过”与“测试失败”区分开。

#### 测试截图与前后对比规范

1. **先截后测，成功必截**：每条用例执行前先截“测试前”图，记录面板、列表和合计的初始状态；用例执行成功后立即截“测试后”图，记录筛选结果、标签状态、请求参数和合计变化。没有截图的用例视为“未验证”，不能记为通过。
2. **统一命名与归档**：截图按用例编号命名，存入固定证据目录，例如 `test-evidence/TC01-before.png`、`test-evidence/TC01-after.png`；截图需保留系统时间或页面时间信息，保证可追溯。
3. **前后对比要能看出差异**：两张图需覆盖同一区域，重点呈现条件面板、选中标签、列表命中行数、合计数值的变化；涉及请求的用例同时保留网络请求参数或接口返回作为佐证。
4. **失败与复验同样留证**：失败用例也要截图记录实际结果；修复后重新执行并重新截取前后图，旧图保留不覆盖，便于追溯改动过程。
5. **证据汇总进报告**：所有截图按用例编号挂接到测试报告，测试报告作为 PR 必附材料和最终验收记录。

### 五：迭代和回退

**失败示例**：AI 将不同字段之间的组合关系猜成“或”，选择“任务模块=力学”和“资源类型=CPU”后，列表出现只满足其中一个条件的任务。界面正常，自动测试也可能因采用相同猜测而通过。

**处理顺序**：

1. 回到待确认问题，拿具体样本请产品确定预期结果。
2. 确认错误在前端参数、后端查询还是两者契约。
3. 让对应角色修正最小范围；主代理处理跨角色影响。
4. 重跑失败用例和相关回归用例，`tester` 复验并重新截取前后对比图、更新测试报告，`reviewer` 复查。
5. 若改动已经扩散或无法定位，回退到该任务开始前的可验证状态，重新拆小范围。

> 迭代不是不断补 Prompt。每次失败都应回到规则、契约或任务边界中的具体一处。如果是需求理解错了，只改代码不改验收标准，下次还会犯同样的错。如果多个 Agent 改了同一处，就要改任务拆分方式，而不是只解决这一次冲突。

### 我的研究结论

**多 Agent 的价值**在于把不同职责的上下文和产物分开：产品梳理规则，规划者安排依赖，前后端实现各自范围，测试者验证行为，审查者独立看风险。真正可以并行的是**文件不冲突、共享契约已确定**的工作。

**可验证的交付**不是“AI 说完成了”，而是需求编号能追溯到任务、代码改动、测试报告（含每条用例的前后对比截图）和最终验收记录。未执行的检查要写“未验证”。

### dev01 实践记录（2026-11-09，Asia/Shanghai）

本次在**一个对话框中创建多个子 agent**，从已合并的 `main` 新建 `dev01`。项目是独立 React 虚构数据演示，没有后端和真实企业/团队身份；PRD 里与真实权限、项目跳转相关的规则没有用演示结果冒充线上验收。任务卡、代码与测试报告随 PR 一起提交。

| 子 agent | 执行内容 | 起止时间（北京时间） | 实际耗时 | 精确 token 用量 |
|---|---|---|---:|---|
| product | 梳理规则、待确认项 | 01:18:22–01:20:42 | 2 分 20 秒 | 不可获取 |
| planner | 契约与文件分工 | 01:20:45–01:23:06 | 2 分 21 秒 | 不可获取 |
| data_logic | 筛选、模型、样例与测试 | 01:23:10–01:29:01 | 5 分 51 秒 | 不可获取 |
| frontend | 面板、标签、表格与测试 | 01:23:10–01:31:16 | 8 分 06 秒 | 不可获取 |
| tester | 首轮验证与修复后复验 | 01:32:10–01:38:11（含间歇） | 5 分 38 秒（实际执行） | 不可获取 |
| reviewer | 独立审查与修复复核 | 01:38:15–01:42:50（含间歇） | 4 分 35 秒（实际执行） | 不可获取 |

截至审查复核结束，子 agent **实际执行时长之和为 28 分 51 秒**；这个数包含 data_logic 与 frontend 的并行时段，不能当作墙上时间。两名实现 agent 同时开始，完成实现用了 **8 分 06 秒**；若简单串行相加为 **13 分 57 秒**，并行重叠 **5 分 51 秒**。串行相加只是算术对照，**不是另一次单对话实测**，不能据此声称整个项目节省了相同时长。

**方案选择**：这个功能涉及规则澄清、独立的数据逻辑和页面实现、测试与审查，在一个对话框内由主代理协调少量子 agent 更方便保留同一任务上下文，也允许互不冲突的代码并行。单文件、小改动通常直接在一个对话框完成更省交接成本。子 agent 的 token 可能因重复读取材料而增加，但本环境没有逐 agent 或整次任务的精确 token 计数接口；**本次无法比较两种方案的 token 消耗**，不填写估算值。

**验证结果**：自动化测试和构建的命令与结果以 `docs/test-report.md` 为准。当前环境的浏览器无法访问本地页面，AC1–AC10 没有按规范取得测试前后截图，因此页面验收均为“未验证”。真实后端权限、正式搜索历史与平台跳转也未验证。

时长展示在演示中按起止时间计算，零小时、零分钟和整分钟的零秒省略；整分钟是否需要显示 `0秒` 待产品确认。
